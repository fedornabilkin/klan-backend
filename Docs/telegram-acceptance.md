# Проверка Telegram-входа на VPS

Для проверки нужны VPS, публичный HTTPS-адрес и отдельный тестовый бот. Если установлен `TELEGRAM_REQUIRE_GROUP_MEMBERSHIP=false`, проверьте, что обычный аккаунт после подтверждения в боте получает роль участника, а аккаунт из `TELEGRAM_ADMIN_IDS` получает роль администратора. Подготовка групп и сценарии проверки членства ниже относятся к режиму с включённой проверкой. Локальные тесты используют подставной Telegram API.

## Подготовка окружения

1. Создайте тестового бота через BotFather и отдельную тестовую группу. Добавьте бота администратором: `getChatMember` гарантированно работает для проверки других участников, когда бот — администратор группы.
2. Подготовьте backend по [deployment.md](deployment.md). Задайте HTTPS-адрес в `APP_ORIGIN`, числовые `TELEGRAM_GROUP_IDS`, если проверка групп включена, и при необходимости `TELEGRAM_ADMIN_IDS`. Сгенерируйте `BOT_INTERNAL_SECRET` и укажите то же значение как `BOT_BACKEND_SECRET` у бота. Задайте `TELEGRAM_BOT_TOKEN` только в конфигурации бота.
3. Compose задаёт `NODE_ENV=production` и `DEMO_MODE=false`. Не включайте демовход ради проверки бота. Токен не должен попадать в `VITE_*`, Git, скриншоты или журналы.
4. Для каждого Telegram-токена используйте только один экземпляр сервиса `bot` с long polling. API больше не выполняет polling. Предыдущий webhook должен отсутствовать. Предварительная проверка сообщит о нём, но не удалит автоматически.
5. Каждый компонент запускается своим Compose или менеджером процессов по собственной инструкции. Для контейнеров на одном хосте создайте сеть `docker network create klan` один раз и подключите `Docker/compose.network.yaml` из каждого репозитория. Backend получает DNS-имя `api`; frontend использует `API_UPSTREAM=api:3001`, bot — `CONTAINER_BACKEND_URL=http://api:3001`. Не используйте адрес `localhost` другого контейнера. На frontend задайте `KLAN_DOMAIN=ваш-домен`, публичные порты 80/443 и убедитесь, что Caddy выдал корректный сертификат, а внешний адрес точно совпадает с `APP_ORIGIN`. За собственным reverse proxy нужны HTTP Upgrade для `/ws`, исходный `Origin` и `X-Forwarded-Proto: https`; доверенным должен быть ровно один proxy hop, как в текущем приложении.

## Предварительная проверка без входа пользователя

Выполните из каталога `Project/` репозитория bot с dev-зависимостями. Укажите свой файл окружения бота. Для проверки групп передайте также `TELEGRAM_GROUP_IDS` из настроек API.

```sh
DOTENV_CONFIG_PATH=../Docker/.env npm run check:telegram
```

Команда читает настройки бота и данные Telegram API. Локальная проверка формата конфигурации доступна через `npm run check:config`.

Команда проверяет:

- ID и имя бота через `getMe`;
- отсутствие webhook через `getWebhookInfo`;
- доступность переданных групп и административный статус бота.

Код завершения 0 означает успешные предварительные проверки. Код 1 означает проблему конфигурации/доступа. Команда не вызывает `sendMessage`, `getUpdates` или `deleteWebhook`, не меняет базу и не создаёт сессии. Она также не доказывает, что другое приложение не использует long polling: это проверяется по запущенным процессам и отсутствию конфликтов в журналах.

## Уровни доступа по группам

`TELEGRAM_GROUP_IDS` — полный список групп, дающих право войти. Достаточно членства хотя бы в одной. `TELEGRAM_GROUP_LEVELS` — JSON-объект; его ключи обязательно должны присутствовать в этом списке. Неуказанные группы дают уровень `member`.

```dotenv
TELEGRAM_GROUP_IDS=-1001111111111,-1002222222222,-1003333333333
TELEGRAM_GROUP_LEVELS={"-1001111111111":"member","-1002222222222":"moderator","-1003333333333":"admin"}
TELEGRAM_MEMBERSHIP_TTL_SECONDS=60
```

Это пример, а не активные ID проекта. Административный уровень давайте только закрытой группе администраторов, а не общей группе сообщества.

| Уровень | Возможности |
| --- | --- |
| member | Просмотр закрытого сообщества и обычные действия участника |
| moderator | Дополнительно управление справочниками и материалами |
| admin | Дополнительно подробная аналитика и управление участниками |

При нескольких группах выбирается наивысший уровень. `TELEGRAM_ADMIN_IDS` повышает уровень до admin только после подтверждения членства в разрешённой группе. Telegram-статус администратора обычной группы сам по себе не делает пользователя администратором сайта. Сервер вычисляет права; импорт профиля или запрос браузера не может назначить их.

После изменения переменных перезапустите API. При изменении членства в Telegram права перепроверяются по истечении кэша (60 секунд по умолчанию; допустимо 15–300). WebSocket перепроверяется дополнительно каждые 30 секунд: существующее соединение может закрыться в пределах срока кэша плюс этот интервал. Удаление из привилегированной группы снижает уровень, удаление из всех разрешённых групп отзывает сессию. Недоступность Telegram после истечения кэша запрещает доступ; восстановление требует нового входа.

## Ручная приёмка с тестовым ботом

Используйте разные браузерные профили/приватные окна для участника и постороннего. Обычный участник не должен входить в `TELEGRAM_ADMIN_IDS` или административную группу.

- [ ] Гость открывает внутреннюю ссылку: появляется экран входа; `/api/users` возвращает 401; WebSocket без сессии не подключается.
- [ ] На странице входа нет кнопки демовхода. `POST /api/auth/demo` с корректным same-origin JSON запросом возвращает 404.
- [ ] Участник начинает вход, видит код и короткую инструкцию в модальном окне, открывает бота и при первом обращении нажимает Start. Бот показывает тот же код и кнопки «Авторизоваться» и «Отклонить». Сессия появляется в исходном браузере после нажатия «Авторизоваться».
- [ ] Сообщение с кнопками показывает адрес сайта с портом и время создания запроса по Москве. После подтверждения или отказа в чате остаются адрес, время запроса и время решения с пометкой «МСК».
- [ ] «Отклонить» завершает ожидание в браузере. Повторное нажатие или закрытие окна входа не может создать сессию.
- [ ] После входа установлена cookie `__Host-klan_session` с `HttpOnly; Secure; SameSite=Lax; Path=/` и без `Domain`. Она не доступна JavaScript.
- [ ] Посторонний получает отказ в боте и не получает серверную сессию. Административный ID, не состоящий ни в одной разрешённой группе, тоже не входит.
- [ ] Подтверждение из первого браузера нельзя получить во втором: идентификатор запроса без исходной browser cookie не даёт сессию. Повторное использование подтверждения не работает.
- [ ] Ссылка старше пяти минут не принимается; новый вход создаёт новый запрос.
- [ ] Если участник вышел из группы между подтверждением в боте и получением сессии, браузер получает отказ.
- [ ] Участник не получает доступ к подробной аналитике и административным изменениям. Moderator получает только свои возможности, admin — полный набор.
- [ ] После удаления из привилегированной группы уровень снижается; после удаления из всех разрешённых групп API перестаёт принимать сессию и WebSocket закрывается в указанные сроки.
- [ ] Выход отзывает текущую сессию; обновление закрытой страницы снова требует входа.
- [ ] После перезапуска API и отдельного бота действующая сессия участника восстанавливается из PostgreSQL и снова проверяется через Telegram.
- [ ] Внешний запрос `/internal/telegram/updates` возвращает 404; прямой запрос к API без правильного внутреннего секрета не принимается.
- [ ] После перезапуска бота offset сохраняется; повторное подтверждение уже использованной ссылки не создаёт новую сессию.
- [ ] Ошибка/таймаут Telegram показывает понятное сообщение; журналы и ответы API не содержат токена, browser cookie или идентификатора сессии.

Результат и дату реального прогона сохраните в `Project/.local/checks/` или отдельном приватном каталоге, исключённом из Git. До такого прогона не отмечайте интеграцию с реальным ботом как завершённую.
