# Klan Backend: правила работы

Backend — самостоятельный репозиторий API. Команды выполняются из `Project/`: `npm ci`, `npm run typecheck`, `npm test`, `npm run build`.

- Используйте TypeScript в строгом режиме и ESM. Импорты между исходными TypeScript-модулями заканчиваются на `.js`.
- Не импортируйте код из соседних репозиториев или служебной папки. Контракты и чистые общие функции хранятся в `Project/src/shared`; изменения публичного API согласуются с frontend и bot через версионируемый HTTP-контракт.
- Маршруты и транспорт находятся в `Project/src/app.ts`; бизнес-правила — в `Project/src/domain.ts` и профильных модулях; доступ к данным — в `Project/src/repository.ts`; авторизация — в `Project/src/auth.ts`.
- Проверяйте права и входящие данные на сервере. Блокировки интерфейса не заменяют серверные проверки.
- Все изменения состояния выполняйте через `Repository.write`; сохраняйте атомарность, откат и существующие инварианты. Сообщения WebSocket отправляются после успешной записи.
- Не меняйте реальные данные, Telegram ID, привязки аккаунтов или роли ради теста. Тесты используют изолированные репозитории и синтетические фикстуры.
- Файлы сборки, запуска и развёртывания, примеры конфигурации и применимые к API эксплуатационные инструменты хранятся в этом репозитории. Они не должны зависеть от соседних каталогов рабочего пространства.
- Не добавляйте в Git токены, реальные `.env`, личные выгрузки, снимки базы или журналы. Локальные настройки и состояние храните в игнорируемой `Project/.local/` либо по явно заданным внешним путям; публичный географический справочник входит в репозиторий.
- Ошибки API должны быть безопасны для клиента. Не выводите сырые объекты клиентов PostgreSQL или URL Telegram с токеном.
- Добавляйте целевые тесты к изменениям авторизации, транзакций и бизнес-инвариантов. Перед завершением запускайте относящиеся к изменению проверки.
- Следуйте [архитектуре](../Docs/architecture.md), [контракту API](../Docs/API-CONTRACT.md), [развёртыванию](../Docs/deployment.md) и [бизнес-правилам](../Docs/requirements.md).

- Соблюдайте структуру: код и npm-конфигурация в `Project/`, Docker/Compose в `Docker/`, конфигурация серверов в `Deploy/`, локальные сценарии в `Scripts/`, документация в `Docs/`, правила в `Agreements/`. В корне оставляйте только README, AGENTS и необходимые Git-файлы.
- Поддерживайте локальный запуск через Node.js без Docker на Windows, Linux и macOS. Docker — отдельный способ развёртывания, а не зависимость разработки.
- Фиксируйте завершённые изменения осмысленными коммитами. Заголовок и поясняющий текст сообщения коммита пишите на русском языке; технические имена, идентификаторы и необязательный conventional-префикс можно оставлять в исходном виде. Например: `Перенесены файлы приложения в Project`.
